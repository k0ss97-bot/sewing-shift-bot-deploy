# Перенос прикладного контура на новый сервер

Дата контрольного снимка: 2026-08-14. Документ не содержит секретов, рабочих баз,
вложений или персональных данных.

## 1. Что переносится

Обязательный прикладной контур:

1. Производственный сайт `www.shagaemfabrika.ru` и редирект корневого домена.
2. Отдельный портал сотрудников `team-shagaemfabrika.ru`.
3. Основная производственная SQLite и закрытые файлы приложения.
4. WMS PostgreSQL `sewing_wms`.
5. Вложения и SQLite портала сотрудников.
6. Caddy, systemd-сервисы, синхронизации, мониторинг и резервные копии.
7. Общий SSO-секрет двух приложений, VAPID-ключи и marketplace credentials —
   только прямым защищённым переносом между серверами, без Git и локального ПК.

Не объединять базы приложений. Портал продолжает читать источник сотрудников
read-only и хранит сообщения, заявки, зарплатные данные и вложения отдельно.

`n8n` сейчас не установлен, поэтому данных n8n для миграции нет. Его следует
разворачивать после успешного переноса в отдельном сервисе, с отдельной БД и
закрытым интерфейсом.

| Backups | ежедневные SQLite, WMS и messenger timers active/enabled |
| Hermes | timer установлен; последний service run в `failed` из-за timeout Telegram |

На старом VPS также работают Apache, MySQL, DNS, FTP и почтовые сервисы. Они не
должны автоматически копироваться на новый прикладной сервер. Корневой домен не
имеет опубликованного MX; поэтому до смены A/AAAA владелец должен подтвердить,
используется ли почта на этом домене. Иначе смена адреса может затронуть доставку
почты по fallback на A-запись.

Legacy-адрес `sewing.161-104-33-59.sslip.io` привязан к старому IP и не является
переносимым DNS-именем. На новом сервере он не используется.

## 3. Требования к новому VPS

Предложенный тариф 8 vCPU / 16 GiB RAM / 160 GiB NVMe подходит для текущего
прикладного контура и оставляет запас для Hermes и начального n8n.

Обязательный минимум для cutover gate:

- Ubuntu 24.04 LTS x86-64;
- 4 vCPU, 8 GiB RAM, диск 120 GiB;
- перед restore не менее 80 GiB свободно;
- Python 3.12, PostgreSQL 16, Caddy;
- статический IPv4; при публикации AAAA — рабочий статический IPv6;
- наружу открыты только 22, 80 и 443;
- PostgreSQL слушает только loopback;
- синхронизация времени NTP;
- отдельное off-site хранилище резервных копий. Каталог на том же диске не
  считается off-site backup.

Рекомендуемый новый диск — 160 GiB NVMe или больше. Нельзя хранить на нём
неограниченное число WMS dump: текущая рабочая БД уже занимает около 27 GiB.

## 4. Что подготовить до окна переноса

1. Создать VPS, root/deploy SSH-доступ и отдельного пользователя эксплуатации.
2. Заполнить приватную копию `deploy/server-migration.env.example` без секретов.
3. Понизить TTL записей `@`, `www` и `team-shagaemfabrika.ru` до 300 секунд не
   менее чем за сутки до переключения.
4. Не менять NS Selectel.
5. Если у нового VPS нет IPv6, заранее запланировать удаление старой AAAA в
   момент cutover; старую AAAA нельзя оставлять.
6. Установить пакеты, пользователей, каталоги и venv. Не запускать timers до
   восстановления данных.
7. Развернуть immutable releases из подготовленных Git bundles или Git remote.
8. Установить unit-файлы обоих репозиториев и конфигурацию Caddy.
9. Передать env-файлы напрямую old-root -> new-root, выставить `0600` и не
   выводить содержимое:
   - `/etc/sewing-web/sewing-web.env`;
   - `/etc/sewing-web/web-push.env`;
   - `/etc/shagaem-team-messenger/team-messenger.env`.
10. Проверить, что общий SSO-секрет и действующие VAPID-ключи не изменились.
    Ротация при переносе разлогинит пользователей и сломает существующие push-
    подписки.
11. Запустить bootstrap gate:

```bash
python3 scripts/check_server_migration_target.py --phase bootstrap
```

## 5. Предварительное восстановление без остановки production

1. На старом сервере принудительно выполнить и проверить штатные backup jobs.
2. Для портала запустить его штатный consistent backup, включающий SQLite и
   uploads.
3. Передать backup-артефакты напрямую на новый сервер по SSH с проверкой SHA-256.
4. Восстановить WMS custom dump в новую пустую `sewing_wms` без `--clean` поверх
   существующей базы.
5. Восстановить SQLite-файлы и uploads в новые приватные каталоги.
6. Проверить владельцев и режимы доступа, не открывая содержимое пользователю
   web/proxy.
7. Выполнить SQLite integrity/quick checks и PostgreSQL migrations/balance
   checks. Проверочное восстановление никогда не направлять на старую production.
8. Сверить SHA-256 переданных файлов и количество миграций. Не использовать
   только размер файла как доказательство целостности.
9. Выполнить restored gate:

```bash
python3 scripts/check_server_migration_target.py \
  --phase restored \
  --expected-sewing-commit <SEWING_RELEASE_COMMIT> \
  --expected-messenger-commit <MESSENGER_RELEASE_COMMIT>
```

До финального окна новые экземпляры приложений не должны выполнять записи,
marketplace sync, reconcile, Telegram send или push.

## 6. Финальное окно переноса

Ожидаемая недоступность — 30–90 минут. Начинать только после подтверждения
restored gate и готового rollback.

1. Зафиксировать UTC-время, старые A/AAAA и active release paths.
2. Остановить на старом сервере timers записи/синхронизации, затем оба приложения.
3. Создать финальные SQLite, WMS и messenger backups после остановки записи.
4. Передать финальные backup и uploads, повторно сверить SHA-256.
5. Повторить restore на новом сервере в чистые целевые хранилища.
6. Запустить PostgreSQL, затем основной сайт и портал.
7. Проверить loopback health, авторизацию, SSO, открытие смены/задания, WMS read,
   messenger login/chat/upload и административный доступ.
8. Включить sync/reconcile/monitor timers. Backup timers включить только после
   первого ручного успешного backup на новом сервере.
9. Выполнить running gate:

```bash
python3 scripts/check_server_migration_target.py \
  --phase running \
  --expected-sewing-commit <SEWING_RELEASE_COMMIT> \
  --expected-messenger-commit <MESSENGER_RELEASE_COMMIT>
```

10. После `READY` сменить A для `@`, `www`, `team-shagaemfabrika.ru`; AAAA
    заменить на новый IPv6 либо удалить.
11. Проверить HTTPS с внешнего устройства, TLS, оба health, login/SSO и запись
    контрольной операции.
12. Старый сервер оставить выключенным для записи, но доступным по SSH не менее
    72 часов. Не удалять базы, env и releases в этот период.

## 7. Rollback

Rollback выполняется, если running gate не пройден, есть ошибки авторизации/SSO,
не совпадают данные, отсутствует WMS, не работает запись или внешний HTTPS.

1. Немедленно остановить timers и приложения нового сервера.
2. Вернуть старые A/AAAA.
3. Убедиться, что новый сервер больше не выполняет фоновые записи.
4. Запустить приложения и timers старого сервера.
5. Проверить старые active release/COMMIT, health, авторизацию, задания, WMS и
   messenger.
6. Не переносить данные, созданные на неисправном новом сервере, автоматически.
   Их разбор выполняется отдельно после доказанной сверки.

## 8. Hermes, n8n и инфраструктура домена

Hermes сейчас развёрнут как unmanaged-файл `/home/deploy/daily_report.py`, а его
последний запуск завершился Telegram timeout. До включения Hermes в cutover gate:

1. поместить код в отдельный закрытый Git-репозиторий;
2. вынести все секреты в root-owned env;
3. добавить явный timeout/retry и безопасный журнал;
4. добиться успешного ручного запуска на старом или новом сервере;
5. только затем запускать target checker с `--include-hermes`.

n8n разворачивается после стабилизации основного переноса. Его редактор не должен
быть публичным без SSO/VPN, PostgreSQL n8n не объединяется с WMS.

Почта, DNS-authoritative service, FTP, Apache, MySQL и панель остаются на старом
сервере до отдельного решения. NS продолжают указывать на Selectel. Если почта
нужна, сначала публикуются корректные `mail` A/AAAA, MX, SPF, DKIM и DMARC; только
после этого меняется корневой A/AAAA.

## 9. Критерий завершения

Перенос завершён только когда:

- running gate возвращает `READY`;
- оба публичных домена отвечают HTTPS 200;
- совпадают ожидаемые commits;
- SQLite/WMS/messenger restore проверены;
- PostgreSQL не доступен извне;
- timers active/enabled и их первые ручные запуски успешны;
- SSO и push используют прежние ключи;
- off-site backup подтверждён;
- rollback path и старый сервер сохранены не менее 72 часов.
