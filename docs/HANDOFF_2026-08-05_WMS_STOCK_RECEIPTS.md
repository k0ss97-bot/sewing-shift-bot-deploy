## Текущее состояние

Код полностью реализован, проверен локально, закоммичен и отправлен в
`origin/codex/wms-integration`. Production **не обновлён**: доступ через
авторизованную серверную консоль в Brave оказался недоступен для Computer Use,
а ранее обычный SSH-ключ этого Mac сервер не принимал.

Не считать задачу развёрнутой, пока не подтверждены отдельно:

1. production runtime-коммит;
2. применение миграции `010_wms_stock_receipts.sql` к рабочей WMS PostgreSQL;
3. перезапуск сервиса и локальный/public health-check;
4. наличие экрана в авторизованном интерфейсе;
5. фактическое проведение документа и появление остатка в `RECEIVE-01`.

## Что реализовано

- Добавлен отдельный экран **Управление складом → Оприходование**.
- Кладовщик может последовательно сканировать несколько зарегистрированных
  товарных штрихкодов, указать количество по каждой позиции и провести всё
  одним документом.
- Неизвестный штрихкод, неготовая продукция, дробное/нулевое/отрицательное или
  слишком большое количество отклоняются до записи документа.
- Одинаковые товары внутри документа объединяются; суммарное количество одного
  товара ограничено `1 000 000`.
- Проведение атомарно: либо все строки, остатки и движения записываются вместе,
  либо транзакция откатывается целиком.
- Каждая позиция увеличивает физический производственный остаток WMS в системной
  зоне `RECEIVE-01` и получает движение `stock_receipt`.
- Повторная отправка того же `request_key` идемпотентна и не удваивает остаток.
- В интерфейсе показываются последние документы оприходования.
- Размещение в адресную ячейку теперь разрешено только из фактически доступного
  остатка того же товара в `RECEIVE-01`, с учётом резерва. Старое прямое
  создание остатка в ячейке через «Размещение» удалено.
- Производственный приход после упаковки продолжает попадать в `RECEIVE-01` по
  прежнему автоматическому контуру.

## Основные файлы

- `miniapp_assets.py` — экран ТСД, сканирование, список позиций, проведение,
  история документов и строгий сценарий размещения.
- `wms/api.py` — `/api/wms/stock-receipts/post` и
  `/api/wms/stock-receipts`, повторное безопасное разрешение штрихкодов.
- `wms/operations.py` — атомарное проведение документа и запрет прямого
  размещения без остатка в `RECEIVE-01`.
- `wms/repository.py` — сохранение заголовка/строк документа и выборка истории.
- `wms/models.py` — `StockReceiptResult`.
- `wms_migrations/010_wms_stock_receipts.sql` — таблицы документов и строк.
- `tests/test_wms.py` — контракты API/UI, атомарность, идемпотентность и строгая
  проверка размещения.

## Как открыть работу на другом ПК

```bash
git clone https://github.com/k0ss97-bot/sewing-shift-bot-deploy.git
cd sewing-shift-bot-deploy
git switch codex/wms-integration
git pull --ff-only origin codex/wms-integration
git rev-parse --short HEAD
```

Ожидаемый HEAD: `ce09d21` или более новый коммит, в котором этот коммит является
предком. Перед действиями прочитать `AGENTS.md` и проверить `git status`.

На исходном Mac остался посторонний незакоммиченный файл
`scripts/import_stock_snapshot.py`. Он не относится к оприходованию, не включён
в `ce09d21` и на другом ПК после clone не появится. Не пытаться воссоздать или
смешивать его с релизом без отдельной задачи.

## Безопасное продолжение и deployment

1. Сверить `origin/codex/wms-integration`, локальный HEAD, текущий production
   runtime-коммит, активный release/symlink, процесс и целевую WMS PostgreSQL.
2. Не читать и не копировать `.env`, базы, логи, exports или секреты. Проверять
   только имена настроек/состояние сервиса утверждённым способом.
3. До миграции сделать и проверить резервную копию WMS существующим скриптом:

   ```bash
   python3 scripts/backup_wms.py
   ```

   Команду запускать в штатном окружении сервиса, где уже задан
   `WMS_DATABASE_URL`; сам URL не печатать.
4. Создать новый изолированный release из точного коммита `ce09d21`, не менять
   файлы внутри старого активного release.
5. В новом release выполнить compile, полный isolated unittest и web smoke.
6. Проверить статус WMS-миграций, затем применить pending migration:

   ```bash
   python3 -m wms.migrate --status
   python3 -m wms.migrate
   python3 -m wms.migrate --status
   ```

   В финальном статусе должна присутствовать
   `010_wms_stock_receipts.sql`.
7. Атомарно переключить release/symlink, перезапустить штатный web-сервис и
   дождаться готовности.
8. Проверить локальный health, затем public HTTPS `/health` и `/app`.
9. В авторизованном интерфейсе открыть **Управление складом → Оприходование** и
   убедиться, что видны сканер, состав документа, комментарий, кнопка
   **Выполнить оприходование** и история документов.
10. Не создавать искусственный production-остаток ради smoke-проверки. Первый
    реальный документ проводить только по фактическому товару и количеству.
    После проведения проверить одновременно документ, движение
    `stock_receipt`, остаток в `RECEIVE-01`, затем размещение в адресную ячейку.

## Откат

Код откатывается атомарным возвратом symlink на предыдущий release и
перезапуском сервиса. Миграция `010` добавляет новые таблицы и может безопасно
остаться в базе при откате кода. Не удалять таблицы и не восстанавливать всю
рабочую БД только из-за отката приложения. Если уже был проведён ошибочный
реальный документ, сначала остановиться и сделать точную выборку документа,
строк, движений и остатков; массовый/ручной SQL-откат без отдельной проверки не
выполнять.

## Критерий завершения

Задача завершена только когда `ce09d21` (или содержащий его следующий коммит)
реально работает в production, миграция `010` применена, public health успешен,
авторизованный экран проверен, а один фактический документ прошёл цепочку:

`Оприходование → RECEIVE-01 → Размещение → адресная ячейка`.
