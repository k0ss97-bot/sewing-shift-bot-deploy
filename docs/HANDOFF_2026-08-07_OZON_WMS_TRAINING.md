## 2. Что сделано с каталогом Ozon

Ozon теперь является каноническим источником карточки для внутреннего каталога, склада и производственной связи:

- название;
- артикул;
- SKU;
- основной и дополнительные штрихкоды;
- размер;
- полный цвет, включая составные значения;
- идентичность отдельной карточки по Ozon `product_id`.

Нижестоящие источники Wildberries, производство и WMS не переписывают поля Ozon и не подменяют его штрихкод. Разные карточки Ozon больше не склеиваются по одинаковому артикулу, штрихкоду или видимому варианту.

## 4. Учебный режим производственных заданий

Требуемая временная логика реализована и включена:

1. Раскройщик завершает `Формирование готового кроя`.
2. Для получившегося годного количества сразу создаются все последующие производственные задания.
3. Задания публикуются независимо и доступны сотрудникам одновременно.
4. Сотрудник может выполнить только часть количества.
5. Невыполненный остаток возвращается отдельным свободным заданием без дубликатов.
6. Физический выпуск готовой продукции и передача в WMS выполняются только на финальной упаковке.
7. Строгие маршрутные карты сохранены и могут быть снова включены администратором.

Текущая production-настройка: `route_execution_mode=training` (`Учебный`). Новые партии после формирования готового кроя автоматически используют эту логику.

Старые задания были созданы до включения режима и первоначально остались строгими. Выполнена отдельная безопасная миграция свободной партии раскроя №6:

- 18 существующих заданий переведены в `training`;
- создано 135 недостающих свободных заданий;
- всего по партии №6 активно 153 задания;
- свободно 153 из 153;
- опубликованы этапы 4–14;
- распределение по этапам: по 15 основных заданий на этапах 4, 5, 6 и 8–14, плюс 3 групповых задания подготовки резинки на этапе 7;
- дубликатов основной номенклатуры/размера/цвета/этапа нет.

Пять старых карточных заданий остаются в строгом режиме намеренно: они не являются свободной сформированной партией №6; одно из них уже находилось в работе у сотрудника. Их не мигрировать автоматически без отдельного анализа остатков и назначения.

## 5. Wildberries — что остаётся

Токен не заменялся и новый токен не создавался.

Фактическое состояние последней полной диагностики:

- каталог и цены доступны;
- FBS-остатки доступны через Marketplace API;
- FBW-остатки отклоняются WB с HTTP 403: `base token without secret is not allowed`;
- для этого пути требуется фактический `X-Client-Secret` базового токена;
- часть остальных разделов временно получала HTTP 429 и соблюдает `Retry-After`;
- ошибки 401/402/403/404/429/5xx не сводятся к одному `permission_required`.

Не предлагать пользователю новый токен без новой фактической ошибки токена. Следующий шаг по WB — получить/установить именно Client Secret для существующего базового токена, затем повторить безопасную диагностику без вывода секретов.

## 7. Как продолжить на другом ПК

Если репозитория ещё нет:

```bash
git clone https://github.com/k0ss97-bot/sewing-shift-bot-deploy.git
cd sewing-shift-bot-deploy
git fetch origin
git switch --track origin/codex/wms-integration
git rev-parse HEAD
git merge-base --is-ancestor 1583921aa264bd8ad29fbb5ea538ea822763353e HEAD
```

Последняя команда должна завершиться с кодом 0. Production-кодовый SHA:

```text
1583921aa264bd8ad29fbb5ea538ea822763353e
```

Если репозиторий уже есть:

```bash
git fetch origin
git switch codex/wms-integration
git pull --ff-only origin codex/wms-integration
git status --short
git rev-parse HEAD
git merge-base --is-ancestor 1583921aa264bd8ad29fbb5ea538ea822763353e HEAD
```

Проверка production без изменения данных:

```bash
ssh root@157.22.204.56 'readlink -f /opt/sewing-web/current'
ssh root@157.22.204.56 'cat /opt/sewing-web/current/COMMIT'
ssh root@157.22.204.56 'systemctl is-active sewing-web.service'
ssh root@157.22.204.56 'systemctl is-active sewing-marketplaces-sync.timer'
curl -fsS https://www.shagaemfabrika.ru/health
```

Перед любым следующим production-изменением:

1. прочитать `AGENTS.md` полностью;
2. проверить ветку, dirty worktree, remote SHA и активный релиз;
3. не включать в commit чужие или неизвестные файлы;
4. создать соответствующую резервную копию SQLite/PostgreSQL;
5. выполнить compile, изолированные тесты и web smoke;
6. публиковать только отдельный immutable release;
7. после переключения проверить внутренний и публичный `/health`;
8. отдельно проверить авторизованный UI-сценарий.
